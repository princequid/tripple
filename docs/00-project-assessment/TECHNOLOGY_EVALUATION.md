## 1. Authentication

**Requirement.** Passwordless email OTP (parity with the original, [04 J4](../reverse-engineering/04-user-journeys.md)), Google sign-in, optional email + password with verification and reset, and server-side sessions in HttpOnly cookies. It must also cover:

- an auth gate that returns the user to `returnTo`;
- usable sessions inside Server Components, Server Actions and Route Handlers;
- persistence in Turso through Drizzle;
- rate limiting on OTP send and verify.

| Option | Fit with Next.js + Turso + Drizzle | Pros | Cons |
|---|---|---|---|
| **Better Auth** (1.7.x) | Drizzle adapter with `provider: "sqlite"` [VERIFIED](https://better-auth.com/docs/adapters/drizzle). The schema is generated by Better Auth's CLI, then migrated with `drizzle-kit generate` / `migrate` [VERIFIED, same page] | **emailOTP plugin** [VERIFIED](https://better-auth.com/docs/plugins/email-otp): sign-in OTP, email verification, password reset, `disableSignUp`, `storeOTP` plain/encrypted/**hashed**. Defaults are 6 digits, 300 s expiry and 3 attempts. Social providers (Google), email + password and a built-in rate limiter with **database storage** [VERIFIED](https://better-auth.com/docs/concepts/rate-limit). The project now also maintains Auth.js and recommends Better Auth for new projects [VERIFIED headline](https://better-auth.com/blog/authjs-joins-better-auth) | Younger API surface with frequent minor releases. The docs do not mention libSQL or Turso explicitly, nor transaction behaviour on them. `storeOTP` defaults to **plain text** and must be set to `hashed`. The in-memory rate limiter is unsuitable for serverless [VERIFIED] |
| **Auth.js** (`next-auth`) | Has a Drizzle adapter [from the lead's findings; not re-checked] | Mature, large ecosystem | The App Router–native v5 is **still beta** (`5.0.0-beta.32`) and `latest` is v4.24.15 [VERIFIED npm]. Now maintained by the Better Auth team, who recommend Better Auth for new projects [VERIFIED headline]. Email sign-in is magic-link-oriented, so OTP codes need custom work [INFERRED]. No built-in rate limiting [INFERRED] |
| **Custom** (doc 07's suggestion) | Full control | No dependency | Security-critical code to write, test and maintain: OTP hashing, timing-safe compare, session rotation, OAuth PKCE and state, CSRF. High risk for a small team |

**Recommendation: Better Auth** (D-04), with:

- **Drizzle adapter, `provider: "sqlite"`**. Auth tables live in the same Drizzle schema and are migrated by Drizzle Kit.
- **emailOTP plugin** with `storeOTP: "hashed"`. `otpLength` and `expiresIn` are a P01 choice; doc 07 proposed 10 min and 5 attempts, while the library defaults to 300 s and 3.
- **Google provider** if D-03 approves it.
- **`rateLimit.storage: "database"`**, with stricter custom rules for the OTP send and verify paths.
- **Email sending** through `sendVerificationOTP`. The docs advise not awaiting the send, to reduce timing attacks, and to use `waitUntil` or similar on serverless. In Next.js that is `after()` (§3).
- **Bot protection** on the OTP request (Turnstile or similar, §7).

**Must be proven in SPIKE-03:** schema generation on SQLite, OTP sign-in end to end against Turso, session reads in a Server Component and a Server Action, Google callback, DB-backed rate limiting, and behaviour when FK enforcement is on.

**Cost:** OSS and free. Google OAuth client is free [INFERRED]. **Status: Pending approval (D-03 methods, D-04 library).**

## 2. Search

**Requirement:**

- R1: full-text shot search (`/search/:term`, title, description, tags) ranked by relevance and popularity; tag pages; empty state.
- R2: designer search (name/username prefix) and header autocomplete.
- R3: services search and colour similarity search.

| Option | Status on Turso | Pros | Cons |
|---|---|---|---|
| **SQLite FTS5** (virtual table, `MATCH`, `bm25()`) | Turso's extensions page lists FTS5 as **always-on** [VERIFIED](https://docs.turso.tech/features/sqlite-extensions) | Standard, well documented. `bm25()` ranking, prefix queries, `snippet()`. Works in local `file:` libSQL for tests [INFERRED] | Drizzle does not model virtual tables, so it needs custom SQL migrations and triggers (or app-side sync) [INFERRED]. External-content tables need careful trigger maintenance |
| **Turso Tantivy FTS** (`CREATE INDEX … USING fts`, `fts_match`, `fts_score`, `fts_highlight`) | Documented [VERIFIED](https://docs.turso.tech/sql-reference/functions/fts). The page explicitly says it **differs from SQLite FTS5**: no `MATCH`, no `snippet()`. It lists limitations: no automatic segment merging, and **no read-your-writes inside a transaction**. The page does **not** state which deployment (Turso Cloud vs the new Turso engine/local) supports it | Index-style declaration (closer to normal schema), BM25 scoring, per-column weights | Engine availability is unclear. Different syntax from FTS5, so the two cannot be swapped transparently. The page's examples order `fts_score` DESC while the text says lower is better; this inconsistency must be tested |
| **`LIKE` / `instr`** on normalised columns | Always available | Zero setup. Fine for prefix search on usernames and tags | No relevance ranking. `%term%` cannot use indexes (full scans count against the row-read quota) |
| External engine (Meilisearch, Typesense, Algolia) | — | Best relevance and typo tolerance | New service, sync pipeline, cost. Deferred |

**Recommendation (D-07):**

1. Put all search behind a **`SearchService` interface** in `src/server` (doc 07 decision 7 carries over).
2. **R1 default: FTS5** with an external-content table over `shots(title, description, tag_text)`, kept in sync by triggers created in a custom Drizzle Kit migration. Ranking = `bm25()` blended with `popularity_score` in SQL.
3. **Designer and tag prefix search:** `LIKE 'q%'` on lower-cased indexed columns.
4. Choose Tantivy FTS instead **only if** SPIKE-01 shows FTS5 is unavailable or deprecated on our Turso Cloud database, or Tantivy is clearly better on that engine.
5. **Colour search (R3):** store each palette colour as CIELAB (`lab_l`, `lab_a`, `lab_b REAL`). Query with a bounding box (`BETWEEN` on indexed L/a/b) and then `ORDER BY` squared distance, so no `sqrt` is needed. SQLean Math is always-on if required [VERIFIED extensions page].

**Cost:** none beyond Turso usage. **Status: Pending approval (D-07), gated by SPIKE-01.**

**Recommendation (D-11), minimal first:**

- **R3:** adopt **QStash** (simple) or **Inngest** (durable steps) when video processing and notification fan-out arrive. Decide then, with measured volumes. Video needs ffmpeg, which is not available as a native binary in typical serverless or Workers runtimes [INFERRED]. Options to evaluate at R3: an external transcoding service, or a small container worker.

All job handlers must be **idempotent** (safe to retry) and live in `src/server` services so any runner can call them.

## 6. R2 access (SDK) and upload flow

**Facts [VERIFIED](https://developers.cloudflare.com/r2/api/s3/presigned-urls/):**

- R2 supports presigned **GET/PUT/HEAD/DELETE** via the S3 API, with expiry from 1 s to **7 days**.
- **HTML-form POST uploads are not supported.**
- Presigned URLs work only on the S3 API domain, **not custom domains**.
- The signed `Content-Type` must match the upload, or the request fails with 403.
- Browser uploads require **bucket CORS rules**.
- Documented SDKs: `@aws-sdk/client-s3` + `@aws-sdk/s3-request-presigner`, and `aws4fetch`.

**Free tier [VERIFIED](https://developers.cloudflare.com/r2/pricing/):** 10 GB-month storage, 1 M Class A ops, 10 M Class B ops per month, **free egress** (Standard storage class only).

| Option | Pros | Cons |
|---|---|---|
| **@aws-sdk/client-s3 + s3-request-presigner** | Typed, full S3 surface (multipart, HEAD, ListObjects). Documented by Cloudflare | Larger bundle. Matters on Workers (3 MiB free / 10 MiB paid compressed limit [VERIFIED OpenNext]), less so on Node functions |
| **aws4fetch** | Tiny, fetch-based, runs in every runtime. Documented by Cloudflare (needs `allHeaders: true` to sign Content-Type) | Hand-written requests for multipart and listing. Fewer types |

**Recommendation:**

- On a **Node host (Vercel)**: `@aws-sdk/client-s3` + presigner.
- On **Cloudflare Workers**: `aws4fetch`.

Either way, wrap it behind a `StorageService` (`presignPut`, `head`, `put`, `delete`) so the choice is reversible.

**Upload flow** (no POST policy means no server-enforced `content-length-range` [INFERRED]):

1. Client asks the server for a presigned PUT. The server validates the declared MIME type and size, creates a `media` row with `status = pending`, and signs the key and Content-Type with a short expiry (~5 min).
2. Client PUTs directly to R2.
3. Client calls "complete". The server `HEAD`s the object to verify size and type, rejects and deletes it if over limits, then runs sharp (§5) and sets `status = ready`.
4. A daily cleanup deletes `pending` objects older than 24 h.

Multipart upload for large videos is an R3 concern.

**Status:** R2 itself is approved (A-03). Account and buckets are pending (D-10). SDK choice pending, tied to D-09.

## 7. Rate limiting and bot protection

**Requirement:** throttle OTP send and verify (per email, per IP), sign-up, likes, follows, comments, uploads and search. Return 429 with `Retry-After`.

| Option | Facts | Assessment |
|---|---|---|
| **Better Auth built-in limiter, DB storage** | Enabled in production by default (10 s window / 100 requests default). Custom per-path rules. `storage: "database"` recommended for serverless [VERIFIED](https://better-auth.com/docs/concepts/rate-limit) | Use it for all auth endpoints |
| **Turso table** (fixed or sliding window: `key`, `window_start`, `count` with an UPSERT) | No new infrastructure | Each limited request costs a **row write**. With 10 M writes/month on the Free plan [VERIFIED §10], rate limiting high-volume reads (search) would waste quota. Adds a DB round trip |
| **Upstash Redis** (`@upstash/ratelimit`) | Free: 500K commands/month, 250 MB, 1 DB [VERIFIED](https://upstash.com/pricing/redis) | Lower latency, purpose-built. A new vendor (free tier). Library details [UNVERIFIED] |
| **Edge/WAF rules** (Vercel Firewall / Cloudflare WAF) | [UNVERIFIED] plan availability | Good for coarse IP-level abuse |

**Recommendation (D-12):**

- Better Auth DB-backed limiter for auth.
- A small **Turso-table limiter for social writes** (likes, follows, comments, uploads). These already cost writes, so the overhead is proportional.
- **No limiter on anonymous reads in R1**, apart from host-level protection.
- Move to Upstash Redis if limiter writes exceed ~10% of the Turso write quota or add measurable latency.

**Bot protection:** add **Cloudflare Turnstile** (or equivalent) to the OTP request form. Doc 07 recommended it, and the original used invisible reCAPTCHA [OBSERVED]. Pricing and terms [UNVERIFIED]; check before adoption.

**Status: Pending approval.**

## 10. Turso capabilities and limitations

Every item below affects the P02 architecture or the P03 schema.

| # | Capability / limitation | Evidence | Architectural consequence |
|---|---|---|---|
| T-01 | **Foreign-key enforcement is OFF by default** ("for SQLite compatibility") | [VERIFIED](https://docs.turso.tech/sql-reference/pragmas) | The DB client factory must enable it, and a test must assert it. |
| T-02 | The FK pragma is **per connection** in SQLite. SQLite also ignores `PRAGMA foreign_keys` inside a transaction (no-op), so it **cannot be set inside a `batch()`**, which is itself a transaction | Per-connection and no-op-in-transaction is standard SQLite behaviour [INFERRED]. The Turso page does not state the scope [VERIFIED absence] | Over remote HTTP, statements may run on separate streams, so a pragma issued once may not apply to later requests [UNVERIFIED]. **SPIKE-02** must determine whether FK enforcement can be relied on. Regardless: services validate parents before writes, deletes are explicit (no reliance on `ON DELETE CASCADE` unless proven), and a nightly orphan-check job runs. |
| T-03 | **Atomic writes:** `@libsql/client` `batch()` runs statements in an **implicit transaction**: all succeed and commit, or the whole batch rolls back | [VERIFIED](https://docs.turso.tech/sdk/ts/reference). Drizzle `db.batch()` supports libSQL [VERIFIED via Drizzle docs search result](https://orm.drizzle.team/docs/batch-api) | **Default write pattern:** `db.batch([insert like, update counter])`. Batches cannot branch on intermediate results, so use `INSERT … ON CONFLICT DO NOTHING RETURNING` and conditional `UPDATE … WHERE` to stay idempotent. |
| T-04 | **Interactive transactions** (`client.transaction("write" \| "read" \| "deferred")`) lock the database for writing until commit or rollback, with a **5-second timeout**. The docs warn of performance impact on high-latency or busy databases. Deferred upgrades can fail if a write transaction is running | [VERIFIED](https://docs.turso.tech/sdk/ts/reference) | Avoid `db.transaction()` on request paths, and never hold one across network calls (R2, email). Use it only in migrations or admin scripts. SPIKE-02 measures Drizzle `db.transaction` over remote. |
| T-05 | **Single writer:** SQLite allows one writer at a time. Only WAL journal mode is supported. MVCC mode is experimental | [VERIFIED pragmas page] | Keep write transactions tiny. Aggregate views into daily rows rather than a row per view. High-write features (views, rate limits) are quota and contention hot spots. |
| T-06 | **No PostgreSQL types:** no native enums, arrays, citext, tsvector, GIN or trigram indexes, `timestamptz` or `inet` | SQLite type system [INFERRED, standard] | Mapping in [PROJECT_ASSESSMENT §7](PROJECT_ASSESSMENT.md#7-data-requirements): `TEXT` + `CHECK` for enums, normalised lower-case columns for case-insensitive uniqueness (`NOCASE` is ASCII-only), integer epoch-ms timestamps, join tables for lists. |
| T-07 | **CHECK constraints can be disabled** by `PRAGMA ignore_check_constraints=1` | [VERIFIED pragmas page] | Never set it. Validate enums in Zod as well (defence in depth). |
| T-08 | **`require_where` pragma** (Turso-specific) rejects `UPDATE`/`DELETE` without `WHERE` | [VERIFIED pragmas page] | Consider enabling it in production connections as a safety net. SPIKE-02 checks compatibility with Drizzle and the auth library. |
| T-09 | **ALTER TABLE is limited** in SQLite: ADD/RENAME/DROP COLUMN only, with restrictions. Changing a column's type, constraints, FK or CHECK requires a **table rebuild** (create new table, copy, drop, rename) | SQLite behaviour [INFERRED, standard]. Drizzle Kit generates rebuild-style migrations for SQLite [INFERRED; confirm in SPIKE-02] | Rebuilds toggle FK enforcement and copy data. Every generated migration must be **reviewed**, tested on a copy of staging data, and backed by a PITR checkpoint. Prefer additive changes. FTS virtual tables and triggers live in **custom SQL migrations**, so rebuilds of `shots` must recreate FTS triggers. |
| T-10 | **Full-text search ambiguity:** FTS5 listed always-on; a separate Tantivy `USING fts` index documented with its own functions and limits ("no read-your-writes inside a transaction") | [VERIFIED extensions](https://docs.turso.tech/features/sqlite-extensions) · [VERIFIED FTS](https://docs.turso.tech/sql-reference/functions/fts) | §2. **SPIKE-01** decides. |
| T-11 | **Always-on extensions:** JSON, FTS5, R*Tree, SQLean (Crypto, Fuzzy, Math, Stats, Text, UUID). sqlite-vec and Regexp are optional on specific plans | [VERIFIED extensions page] | JSON functions are allowed for non-queried metadata. SQLean Math helps colour distance. Avoid relying on plan-specific extensions. |
| T-12 | **Embedded replicas** (local file replica, read-your-writes for the writing replica) **cannot be used in serverless environments without a filesystem** | [VERIFIED](https://docs.turso.tech/features/embedded-replicas/introduction) | On Vercel the app uses a **remote connection only**, so every query is a network round trip. Co-locate regions, avoid N+1 queries (use joins/batches), and cache public pages (ISR / `revalidateTag`). A container host could use embedded replicas later. |
| T-13 | **Quotas, Free plan:** 100 databases, 5 GB storage, **500 M rows read/month**, **10 M rows written/month**, 3 GB syncs, **1-day point-in-time restore**. **Developer plan $4.99/mo: 10-day PITR** | [VERIFIED](https://turso.tech/pricing) | Index every feed and filter query: rows *scanned* count as reads [INFERRED from the billing model]. Use counter caches instead of `COUNT(*)`. Use daily view aggregates. A 1-day PITR window is thin for production, so plan the **Developer plan before launch** (cost approval) plus periodic logical exports. |
| T-14 | **Row and blob size:** SQLite supports large blobs, but Turso's own limits are [UNVERIFIED] | — | **No binaries in the DB** (A-03). Keep rows small; long text (descriptions, job HTML) is fine. Store palettes as rows, not blobs. |
| T-15 | **Encryption at rest pragmas are experimental** | [VERIFIED pragmas page] | Do not depend on DB-level encryption features. Hash secrets (OTP, tokens) in the app. |
| T-16 | **Synchronous modes:** only OFF and FULL; OFF risks corruption | [VERIFIED pragmas page] | Never set `synchronous=OFF`. |
| T-17 | **IDs and ordering:** `INTEGER PRIMARY KEY` is the rowid alias. AUTOINCREMENT prevents reuse at a small cost | SQLite [INFERRED] | Numeric public IDs for shots, jobs and collections (URL parity). Text UUIDv7 for media and auth tables (the auth library may dictate). Cursor pagination on `(sort_key, id)`. |
| T-18 | **Local development and tests** can use a `file:` libSQL database with the same client [INFERRED from the libSQL client design] | — | Integration tests run against a temporary file DB with migrations applied, so no network is needed. Confirm FTS parity between local and cloud in SPIKE-01. |

## 14. Client data fetching

**Requirement:** SSR public pages; infinite feeds; optimistic like, save and follow with rollback; little client JavaScript.

| Option | Assessment |
|---|---|
| **Server Components + Server Actions + `useOptimistic` / `useTransition`** | Covers page data, mutations and optimistic toggles natively. Cache invalidation via `revalidatePath` / `revalidateTag` |
| + **small custom infinite-scroll hook** calling a cursor-based Route Handler (`GET /api/shots?cursor=`) | Simple for R1 (append-only lists, no cross-component cache) |
| **TanStack Query v5** (5.107.x) | Valuable when many client components share and refetch server state (notifications, messaging, composer autosave). Adds a second (client) cache layer that overlaps with RSC caching |

**Recommendation:** **no TanStack Query in R1.** Use RSC + Server Actions + a custom infinite-scroll hook. Re-evaluate at R3 (notifications, messaging polling), where TanStack Query (or SWR) earns its weight.

**Status: Pending approval (P02).**
